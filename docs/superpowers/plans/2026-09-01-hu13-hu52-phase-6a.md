# HU-13 and HU-52 Phase 6A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Add bounded, non-blocking patient duplicate warnings and create real patients inline from the appointment form without changing the clinical schema or appointment workflow.

**Architecture:** A single PostgreSQL-backed duplicate service will normalize phone and name inputs, query at most ten `Patient` rows, and expose a minimized endpoint. Both the full patient form and a focused appointment quick-create dialog will call that endpoint and share one warning dialog; quick-create will reuse `POST /api/patients/` with an explicit minimal-response mode and the existing HU-53 identity/profile rules.

**Tech Stack:** Django 5.2, Django REST Framework, PostgreSQL, React 19, Vite, Vitest, Testing Library.

## Global Constraints

- Implement only HU-13 and HU-52, in that order.
- Preserve exact normalized `identification_type + identification_number` enforcement in PostgreSQL.
- Duplicate warnings use only phone and exact normalized first name + first surname + date of birth.
- Include active and inactive patients, consolidate matches, order stably, and return at most 10.
- Do not load clinical records or expose clinical, guardian, document, odontogram, alert, or full identification data.
- Reuse the real `Patient` model and normal appointment creation endpoint; create no provisional entity.
- Create zero models, zero fields, zero migrations, and zero new indexes.
- Keep HU-54 remote patient search intact and never download all patients.
- Do not implement HU-17, merging, reactivation, fuzzy matching, trigram matching, billing, or later stories.
- Preserve the restored PostgreSQL baseline and execute destructive verification only through test databases or transaction rollback.
